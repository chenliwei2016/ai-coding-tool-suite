# Architecture Design

把模糊的需求/想法转化为结构化、可落地的系统技术方案。

## 适用场景（when）

- 接到一个功能/需求，需要产出整体技术方案
- 需要在**多个对象上重复实现同一种能力**（抉择：只做一份 vs 抽取通用层）
- 需要拆分模块、分层、设计组件与调用关系
- 需要决定"写死一堆分支"还是"参数化/抽象设计"
- 改树结构、导航、布局这类**横切所有页面**的结构时

## 输入（要拿什么进来）

- 需求/业务目标、约束与验收标准
- 现有代码结构与既有模式（先探索，别凭空设计）
- 涉及的范围与影响面

## 核心步骤（流程）

1. **先理解现状，再动手**：通读相关代码，识别既有模式与约定，明确改造范围
2. **识别重复**：发现"多个对象上同构的实现"，优先评估"抽一个可复用单元"，而不是复制 N 份
3. **先想后做**：动手前复述对业务/现状的理解，列出不确定点，重要方案先与用户确认
4. **参数化优于写死**：面对"可扩展到多类型/多元素、且增长方向明确"的维度，优先设计成按参数/类型动态适配，而非写死分支
5. **控制改动粒度**：横切性改动（树/导航/布局）先评估影响面，小步实施

## 评审/自检 checklist

- [ ] 是否复用了现有能力，而非造重复轮子？
- [ ] 通用实现是否真的通用（换一个场景仍成立），还是过度抽象？
- [ ] 多对象同构 → 是否抽了可复用组件/函数（而非复制）？
- [ ] 可扩展维度 → 是否参数化而非写死（字段级标签/枚举映射等）？
- [ ] 横切结构改动 → 是否列了影响面并小步走？

## 常见坑

- ❌ 一上来就写代码，没先看现状 → 与既有模式冲突、返工
- ❌ 复制粘贴 N 份 → 共性问题要改 N 处，一个不抽，全要跟着改
- ❌ 面对"多类型/多元素且增长方向明确"却写死分支 → 新增类型时到处加分支，越加越乱
- ❌ 过度通用 → 为了抽象而抽象，虚增复杂度

## 产出物

- 技术方案/设计说明（含范围、结构、权衡、落地步骤、验收标准）
- 对可复用单元的抽取与复用说明
